Day 2 · cold open

What is wrong with this email?

Open the day cold — no framing, no theory. Put this on screen and ask the room: "what's wrong with this email?" Let them hunt for 60–90 seconds. They will guess the usual suspects: the Nigeria sign-in, the urgency, the button, the footer. Say no to each — all of that is copied verbatim from the real Microsoft alert, and a real one genuinely does list a foreign sign-in. Exactly one thing is wrong. Then drive the magnifier across the header line and stop on the sender: account-security@rnicrosoft.com — r + n, not m. Open the Glyph lab and drag the size slider from 13 px upwards with both addresses stacked: at reading size they are the same shape, and only at ~24 px does the pair split apart. Switch the font to Serif and then Mono — in a monospace font the trick dies instantly, because every glyph gets the same width. That's the mechanism: this is not a spelling mistake, it's a typography attack on how we read — we match word shapes, we don't spell-check senders. Land three things before moving on: (1) the display name (“Microsoft account team”) is attacker-controlled free text and the inbox list never shows the domain at all; (2) the tell was one pixel-level detail in a message that was otherwise perfect — you cannot win this by being careful; (3) so the fix is structural, not vigilance: never act from the message, go to the site yourself. Name the family — homoglyph / look-alike domain (rn/m, l/I, 0/O, and Unicode lookalikes like Cyrillic а) — and promise they'll build one of these themselves in the lure sandbox later today.

Day 2 · The First Foothold

Every breach starts with
one way in.

Yesterday you learned what a system is supposed to protect. Today you switch sides: you are the attacker. Before you can touch anything inside, you have to find a target, learn it, and get through the door — without ever "hacking" in the movie sense.

Set the role-play: for the next three days they are the attacker. Today is only the entry — pick a target, study it, get the first foothold. We stop the moment we're inside; what happens next is Day 3.

The road to a foothold

You don't start inside — you earn your way in

Today's job: gather what's public (recon), turn it into a way in — a lure, a weak password, an exposed service — and land the first foothold. The attacker's real advantage isn't a tool, it's information: almost everything they need, you left in public.
Walk the strip left to right — the four teal stages are today, the faded one is Day 3. Before you touch anything

Rules of engagement — the line you don't cross

Always fine

  • Reading what someone published: Google, WHOIS, DNS, certificate logs
  • Searching a scan database like Shodan
  • Checking your own email on Have I Been Pwned

Only with written permission

  • Port-scanning a host you don't own
  • Trying a login — even one
  • Sending a phishing test to real people

Never

  • Using credentials that aren't yours, even if they're public
  • Opening data that leaked but isn't yours
  • Profiling a classmate who didn't ask you to
Finding is legal. Accessing is not. Today you OSINT yourself and public company data; every attack you run is against our sandbox. To practise for real, use ranges built for it — TryHackMe, Hack The Box, VulnHub — or a bug-bounty programme's written scope.
Do not skip this — the next two slides send them to run real searches on real people and real companies. Land the one-line rule: finding is legal, accessing is not. The middle column is the one that surprises people — a single unauthorised login attempt is already the offence in most jurisdictions; intent doesn't matter. The third column is about other humans: the self-OSINT exercise is powerful precisely because it's consensual — turning it on a classmate is not. Point at the legal practice ranges so the answer to "where can I try this?" is concrete.

Recon · Google dorking

Turn Google into a precision recon tool

Everyone can type words into Google; almost no one uses its operators. Build a query live and watch the plain-English line explain exactly what each operator narrows. Then run the missions FOR REAL on their own devices (they're online): find a recruiter at a company they want, find open jobs, price-hunt something they want — then the attacker's version: exposed files that were left public by accident. Land two things: (1) operators turn a vague search into a scalpel, and (2) an enormous amount leaks into Google by accident — which is exactly why the next step, OSINT on yourself, matters. Ethics: finding public pages is legal; opening data that isn't yours is not.

Recon · the target's machines

From one domain name to their whole attack surface

Dorking found their documents; this finds their machines — and all of it is still passive. Run the sources left to right and let the map build. What each one is: WHOIS = the public registration record. DNS = the public phonebook (the MX record hands you their mail provider, so your fake login page knows which brand to copy). crt.sh = certificate transparency: every HTTPS certificate ever issued is written to a public append-only log, so every hostname they ever secured is searchable — this is where "jira-internal" falls out, and nobody ever meant to publish it. Shodan = someone else already port-scanned the whole internet and sells the database; reading it is passive for you (make this nuance explicit — the scan happened, but not by you, so the target sees nothing). GitHub = a committed key lives in the history forever, and every commit carries a real employee's name and email. Land the ending: zero packets sent, and the map already names the exact box and CVE they'll attack in the console later.

Recon · turn it on yourself

Now OSINT the easiest target you have: you

The dork skills they just learned point at a company — now aim them at themselves. Everything is offline and private: what they type never leaves the browser (say this out loud — real email/phone). Have them fill their own identifiers and watch the exposure cards light up, then actually run the check links on their own devices (they're online): Have I Been Pwned for the email, WhatsMyName for the handle, Google dorks for name/phone. The payoff is the cascade banner (email + reused handle): one breach becomes total account takeover — the danger is the LINKS between leaks, not any single one. The real toolkit — name these out loud, it's what they'll actually go and try: Epieos (paste an email or phone, get back which services it's registered on and the Google account name/photo behind it — the dashed chips; free tier needs a signup and it logs the lookup, so demo it yourself on the Layla persona rather than making thirty students hand it a real address), holehe (same idea as a CLI — asks 120+ sites' password-reset flow "does this email exist here?" without notifying the owner), Sherlock (CLI username sweep, the scriptable WhatsMyName), PhoneInfoga (phone → carrier, region, footprint) and Maltego (the graph tool that draws exactly the link-map this widget is teaching). Mention PimEyes as a face search that exists — don't have them upload their faces. Close on the empowering half: every card has a "shrink it" fix. This is the defender's mindset sneaking into the attacker's week.

Weaponise · build the payload

Weaponise: the payload the lure carries

The missing kill-chain stage: weaponise = the payload the lure carries. Drive each tab live: (1) Credential harvester — type in the fake login, watch every keystroke mirror to the attacker's console; (2) Malicious attachment — click "Enable Content" and the hidden macro runs a reverse shell (then flip the "macros blocked" toggle and it dies); (3) Malicious link — hover the Google-looking link to expose the real g00gle-drive.ru destination, and expand a short URL; (4) Malicious QR — you can't read it by eye; "scan" it to reveal the phishing domain. The through-line: a payload must be believable AND evasive — the tension they tune in the lure next.

Deliver · the human exploit

Social engineering: hack the person, not the machine

Social engineering = manipulating people into breaking security — handing over information, clicking a link, or granting access. No firewall stops it, because it targets trust. Every lure below pulls one or more of these five levers.

Authority

We obey people who seem in charge.

“This is IT — reset your password now.”

Urgency

A deadline stops us thinking.

“Your account closes in 24 hours.”

Scarcity

Fear of missing out overrides caution.

“Only 3 offer slots left.”

Familiarity

We trust the known — a brand, a colleague.

“Hi, it's Sara from Finance…”

Fear

Panic makes us act, then verify.

“Suspicious login — secure your account.”
Phishing is social engineering at scale. When you build a lure in two slides' time, notice which levers you're pulling — and why they work on all of us.
The umbrella concept before phishing. Land: social engineering targets trust, not tech — which is why it beats every firewall. Walk the five levers fast; they'll recognise all of them from real messages. Point forward: phishing = these levers delivered by message, at scale. Ask the room which lever fooled them last.

Definition first: phishing is a fraudulent message impersonating someone you trust to make you click, log in, or pay. Deliver · social engineering

Build the lure: believable enough to click, quiet enough to slip filters

Hand them the attacker's console. Have them toggle the cheap tricks first (urgency, look-alike domain, masked link) — watch click-likelihood rise but the red-flag score rise with it, and the defender panel name each tell. Then toggle Personalise (OSINT) alone: click-likelihood jumps, red-flag score barely moves. That's the lesson — the detail that makes a lure land came from the recon they'll do earlier in the day. Deliver · when MFA isn't enough

The phish that beats MFA — and what stops it

The modern correction to "just turn on MFA". The attacker's page isn't a copy — it's a live proxy sitting between the victim and the real site, passing every message through. Run SMS code and then App push: the code is real, current, and typed by the real user, so relaying it works; push is worse, because she genuinely started this login so the prompt looks exactly right. She isn't careless. Then point at the pocket: the prize isn't the password, it's the session cookie the real site issues after MFA succeeds — replay that and you're in, no MFA asked, and it keeps working even after she changes her password. (That's why incident response revokes sessions, not just resets passwords.) Now switch to Passkey and run it again: the browser signs a challenge bound to the site's real address, the victim was on falcon-ta1ent.com, so the signature is worthless. The pocket is empty. Land it: phishing-resistant MFA (passkeys / FIDO2) is the only option here that fails closed — the human can still be fooled, the maths cannot.

Foothold · the foundation

How passwords actually get attacked — all four ways

People say "they cracked the password" as if it were one thing. It's four, and they behave completely differently. Run each with defences off first. Brute force really enumerates the space — watch the odometer spin through 25,895 real combinations to reach a 3-character password, then say the scale out loud: 8 characters is 2.8 trillion. Length beats it; nothing else has to. Dictionary doesn't try everything, it tries what people actually pick. Both hammer one account — so turn on lockout and watch both die instantly. Now the important half. Leave lockout ON and run credential stuffing (real breached pairs, one attempt each) and spraying (one popular password against everyone, one attempt each). Lockout never fires — one attempt per account never looks like an attack. That is the punchline: the control everyone reaches for does nothing against the two attacks that actually scale. Then show what does: unique-per-site kills stuffing outright; MFA kills all four; and note that unique passwords do not stop spraying, because those people each independently chose the same obvious password. This is where the hydra command in the next console comes from.

Foothold · the foundation

A “shell” is a command line on someone else's machine

The word the whole day builds to, defined at last. A shell is just a command interpreter — you type, the machine runs it, it answers. Getting one over the network means you can type on their computer. Once it opens, actually type into it: whoami, id, ls, then sudo -l — the last one leaves a crumb Day 3 picks up. Drive the three shapes. Bind: the target listens, you dial in — and the firewall drops it, because inbound is filtered. Reverse: flip the direction, the target dials you on 443, and it walks straight out, because outbound is trusted and it looks like ordinary HTTPS. That single asymmetry is why practically every real intrusion uses a reverse shell. Web shell: a script in the web root, so commands ride a port that was already open. Toggle the firewall rule off and watch the bind shell suddenly work — the control, not the attack, was the deciding factor. Now the terminal in the next slide will read as something they understand rather than movie noise.
