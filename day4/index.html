Day 4 · Breaking the App

The one door you're
invited to knock on.

A locked network keeps you out. A web app is different — it is built to take input from strangers and act on it. Today the target isn't a person or a wire; it's the application's own logic. Almost every attack you'll drive comes down to one flaw: the app trusted input it never should have.

Reframe the target. Days 2–3 were people and networks; today it's the software itself. The whole day has ONE spine: an app takes untrusted input and mistakes it for trusted instructions. Every vuln (injection, XSS, IDOR) is a broken trust boundary. Keep coming back to that sentence. Self-contained: don't lean on Day 3 being taught.

Foundations · how the web works

Before you break it: what actually happens when you load a page

The load-bearing foundation — everything today abuses this model, so build it deliberately. Drive one request end to end: the browser (client) sends an HTTP request → the app server runs code → it asks the database → a response comes back and the browser renders it. Keep it at the level of the three tiers here; the next two slides take the request apart field by field, so don't pre-empt them. Land the two facts the rest of the day needs: (1) three tiers — browser, server, database; (2) the request is just text the client composes — which means the client can compose ANY text. That is the seam we pry open next.

Foundations · reading the address

A URL is six fields — and you type every one of them

Everything after this slide points at a URL, so read one properly first. Click the six parts in order: scheme (decides the default port and whether there's TLS), host (DNS resolves it, and it comes back as the Host header — one machine serves many sites, so sub-domains like admin. and staging. are separate apps to enumerate), port (8080/8443/3000 is where forgotten staging apps live), path (the resource — and that trailing number is a database id), query (key=value pairs after the ?, joined by &), fragment. Two beats to land. (1) Press + on the invoice id: you just asked for someone else's invoice by editing a number, and the server handed it over — that is IDOR, arriving four slides early and by accident. Say it: the id is data you typed, not a fact. (2) Press "Watch it get sent" and point at the fragment falling away — #items never leaves the browser. That's why a payload placed there appears in no server log at all (DOM XSS), and it's the first hint that the URL you see and the request that travels are two different things. Flip http/https to show the connection line change: same request, no TLS, cookie in the clear.

Foundations · what a message looks like

The request is plain text — and the payload is JSON

Students see JSON in every widget today and in the tamper lab they'll edit a JSON body — teach it before they need it. First the shape: hover the four numbered zones. ① request line, ② headers (key: value, one per line), ③ a blank line — the only thing separating headers from body — ④ the body. Stress that the whole thing is ONE block of text the client typed; nothing in it is signed or verified (the footer line under the request says exactly that, use it). Then JSON, on the GET tab: the parsed panel shows the entire language — string, number, boolean, null, array, object, and objects nesting inside objects; keys are always quoted strings. Hit "edit this body", delete a quote, and show the whole message becoming unreadable — then say the callback out loud: that is exactly what one stray apostrophe does to a SQL query. Then the other tabs, fast: POST shows Content-Type/Content-Length (bytes, not characters — the 👍 costs four); /login shows a form does NOT send JSON, it sends key=value&key=value, with the password sitting there in plain text and Set-Cookie coming back; /product/42 shows a response body that is HTML, with the user-typed part in red — the app pasted a stranger's text into your page. Leave that one on screen for a second; it's the seed of XSS.

Foundations · the third tier

Where the data lives — and the four things you do to it

The tier the deck kept pointing at without ever opening. Structure first, then all four operations — and the statement panel updates as you touch the controls, so they read real SQL long before they have to write any. Structure (SELECT tab). (1) It is a separate program, usually its own machine; the app stores nothing itself, so restart the server and the data is still there. (2) A table is a grid — a row is one record, a column one field. Click through users / invoices / reviews. (3) The id is the primary key, unique, one per row — and here is the payoff: that is the number you just saw at the end of the URL. The address bar and the database row are the same thing seen from two ends. (4) Foreign keys: follow the dashed arrows, invoices.user_id → users.id. Click invoice #1043 and read the owner line — user_id 4 → omar, not you. Say it plainly: the database knows perfectly well whose row this is; the app simply has to ask. Park it — when IDOR arrives, the bug is not that the database was fooled, it is that nobody asked it the ownership question. Then the four verbs, quickly. SELECT: pick columns, set a filter, run — what comes back is a result set, some rows and some columns, never the table; the database does the searching. INSERT: add a row and point at the reply — no data comes back, only a count and the new id, which the database chose, not the app. (On the users table set role to admin and ask where that value would come from on a real signup form.) UPDATE: SET says what to change, WHERE says which rows; the old value is simply gone. DELETE: removes whole rows. Then set the filter to (no filter) on a DELETE and run it — the whole table, no undo. Last thing, and it sets up the injection slides: look at the statement panel and note that text values sit inside quotes and numbers do not. Those quotes are a fence. Don't explain it further here — just make them see it.

Foundations · the verbs

A request has a verb: what you're asking the app to do

Where the verb lands: GET→SELECT · POST→INSERT · PUT/PATCH→UPDATE · DELETE→DELETE — the four things any app does to stored data. You'll write those sentences yourself before we break one.
Methods are not trivia — they're the vocabulary of every API attack. Walk the five: GET reads and changes nothing (safe); POST creates (send it twice, you get two — that's the double-charge bug); PUT replaces the whole item; PATCH edits part of it; DELETE destroys it. Drive them live and watch the stored reviews actually change, and watch the status codes come back (200, 201 Created, 204 No Content, 404) — that pre-teaches the next slide. THE BEAT TO LAND: the website only draws a delete button on your OWN review, but the API is a separate door — send DELETE at Layla's review #1 and it just works. The button was never the security. Then flip "API checks ownership" → 403. Say the line: the UI is not the app; the API is the app.

Foundations · what comes back

Status codes: the server tells you more than it means to

First the four families: 2xx worked, 3xx go elsewhere, 4xx YOUR fault, 5xx the SERVER's fault. Then run the probe — these are paths nobody linked to, just names attackers always guess. The reveal is that the codes alone draw a map: /admin answering 403 instead of 404 proves the admin panel EXISTS (a refusal is a confirmation); /api/users answering 401 says "log in and I might" — also a confirmation. Draw the 401-vs-403 line explicitly: 401 = who are you, 403 = I know you and no. That is authentication vs authorisation, and it comes back on the broken-auth slide. /backup.zip returning 200 is the jackpot. /api/debug returning 500 leaks framework and version — which names the exploit to look up. Then flip "hardened": everything you can't see answers 404, identical to things that never existed, and the map goes dark. Note the widget stays honest — the 500 still leaks, so debug output must be off in production.

Foundations · how it knows who you are

HTTP forgets you — the cookie is the only thing that remembers

The concept that makes cookie theft matter. HTTP is STATELESS — the server has no memory between requests. So at login it issues a session cookie and writes it in a table; every later request just presents that cookie. Drive three beats: (1) delete the cookie → 401, you're a stranger again one second after logging in; (2) your cookie → your account; (3) paste the stolen cookie → you ARE Noura, and you never knew her password. That's session hijacking, and note the stolen value is exactly what the XSS payload will steal two slides from now — same string, deliberately. Then flip to "predictable session ids": the ids just count up, so press + and walk into the next account with no theft at all. That is the "weak session tokens" bullet from the broken-auth slide, made real. Land: the cookie IS your identity — protect it (HttpOnly, Secure, random, short-lived) or anyone holding it is you.

Foundations · the input surface

Five places your input enters — and you control all five

Path url

Which resource you're asking for — usually ending in an id.

/invoice/1042

Query ?a=b

Parameters after the ? — visible in the bar.

?id=42&sort=date

Body post/patch

The payload — JSON, or a form's key=value.

{"price":0.01}

Headers metadata

Who you claim to be, what you accept.

User-Agent, Referer

Cookies identity

Your session — the one you just stole.

session=a3f9…
You have now watched all five leave your own machine. Not only the form fields — the path, the headers and the cookie too. Anything that arrives at the server is a claim, never a fact.
And no, HTTPS doesn't save you. The padlock encrypts the pipe so nobody in the middle reads or edits it. It says nothing about the app at the other end — you're the legitimate sender, and your injection travels perfectly encrypted.
The bridge that closes the foundations block and opens the trust boundary. A taxonomy, so it's cards, not a fake interactive — and by now it is a recap, not new information: they have seen every one of these five on screen (path and query in the URL slide, body and headers in the wire-format slide, the cookie in the session slide). Say that out loud — "you've already watched all five leave your machine." The point learners miss is that "input" means only form fields; name the whole surface, and map each attack to its channel: SQLi via body/query, XSS via body, IDOR via path/query, session hijack via cookie. The HTTPS myth-buster matters — students routinely think the padlock means "safe site". Say it plainly: TLS protects data IN TRANSIT from a third party; it does nothing about what the application does with the data once it arrives. An HTTPS site can be trivially injectable.

The core idea · never trust the client

Everything on the client side is yours to rewrite

The single most important idea of the day. Where does code run? HTML/JS/the form all run in the BROWSER — fully visible and editable by the attacker. Only the server side is out of their hands. So any check done in the browser (a disabled button, a hidden price field, "max qty 10" in JavaScript) is a suggestion, not a control. Drive it: intercept the checkout request and edit price=899→0.01, qty=1→-1, role=user→admin; the server trusts it and obeys. Then flip "server re-validates" and the tampered request bounces. Land: validation that isn't on the server isn't validation. This is the lens for injection, XSS and IDOR next.

The landscape · where apps break

The same flaw, wearing five different masks

Injection A03

Your input is glued into a command — SQL, a shell, an LDAP query — and runs as code.

You'll drive: SQL injection and OS command injection.

Cross-site scripting XSS

Your input is written back into a page and runs as script in someone else's browser.

You'll drive: steal a logged-in victim's session cookie.

Broken access control A01

The app checks what you asked for, never who you are. Change the id, get their data.

You'll drive: read another customer's invoice (IDOR).

Broken authentication A07

Weak passwords, no rate-limit, guessable sessions — the front door barely latched.

Credential stuffing with the breach dumps from Day 2.

Security misconfig A05

Debug pages, default creds, verbose errors, an open admin panel left facing the internet.

The recon skills from Day 2 find these first.
Different names, one root cause: the app treats attacker-controlled input as trusted. Two more you'll meet by name, same family: SSRF — make the server fetch a URL you chose; DOM XSS — XSS built entirely by the page's own JavaScript, never touching the server.
The map before the deep-dives — a taxonomy, so it's text, not a fake interactive. These map to the OWASP Top 10 (mention the framework, don't drill the whole list). Don't lecture all five; land the pattern that unifies them — untrusted input treated as trusted — and flag which they'll actually drive (injection ×2, XSS, CSRF, IDOR). SSRF and DOM-XSS get a one-line name-check so they're not strangers later; don't deep-dive them today. The last two cards tie back to Day 2 (stuffing, recon) so the week connects.

Foundations · the language behind the app

SQL: the sentence your app writes to the database

The next slide is a magic trick without this one — admin'-- is unreadable unless you already know what a quote and a comment do. Ten minutes, four beats. (1) It's a sentence: what to do, to which table, to which rows. Run SELECT with role = 'admin', then id > 2, then untick WHERE — the clause is tested against every row and the true ones come back. Toggle the column chips so they see the app choosing what it asks for. Point out this is the same table the injection sandbox uses, and the same four verbs as the API slide: GET→SELECT, POST→INSERT, PUT/PATCH→UPDATE, DELETE→DELETE. (2) Writes are just as easy: INSERT a new user and set the role to admin — one row, and they're staff; then UPDATE sara's role, then DELETE. Untick WHERE on a DELETE and wipe the table, because "one forgotten line" is a real outage story. (3) THE BEAT THAT MATTERS — the quotes are a fence. Watch the ruler under the statement: └─ the data ─┘. The apostrophes are not part of the value; they are the marker telling the database where data stops and command resumes. Hit the red preset sa'ra: the fence closes early, the leftovers are read as SQL, 1064 syntax error, nothing runs. (4) Hit the other red preset: everything after -- is a comment the database throws away — a whole condition can be deleted by typing two characters. Land it: a quote ends the data, and a double-dash deletes the rest of the sentence. Now turn the page — that is the entire trick.

Injection · the classic

SQL injection: type into a login box, rewrite the query

The centrepiece — and the previous slide did the teaching, so open by calling it back: behind this login is the same kind of sentence they just wrote, over the same four rows, except the app BUILDS it from your input — SELECT * FROM users WHERE username='…' AND password_hash='…'. If it glues your text straight in, your text is inside the fence, and it can BE part of the query. The four presets are numbered because they are the real attacker's order — walk them: (1) NORMAL LOGIN, so they see the honest case; point out the password is hashed BEFORE the query is built, so that box can't carry SQL — the username is the hole. (2) PROBE WITH ONE QUOTE: a single ' and the database throws a 500 syntax error. Dwell here — this is how the bug is FOUND. The error proves your text reached the query and it names MySQL; it's the same "500 leaks internals" lesson from the status-code slide. (3) ADMIN: admin'-- closes their quote and the -- comments the password check away entirely — logged in as admin, no password. (4) MATCH EVERY ROW: ' OR '1'='1' -- turns the WHERE always-true, so all four rows match and the app logs you in as the first. Watch the query rewrite live as they type — that's the reveal you can't just tell them. Note the table on screen is the SERVER's view, not something the login page shows you; pulling data onto the page is UNION SELECT, which needs a page that DISPLAYS results (a search box), so name it and move on. Then flip "parameterised query": the same input is sent as a bound VALUE — injection dies. Land: concatenation is the bug; parameterisation is the fix; real DBs are millions of rows but the mechanism is identical.

Injection · straight to the operating system

Command injection: from a text box to a shell on their server

The attack map promised injection means "SQL, a shell, an LDAP query" — here's the shell one, the highest-impact web bug because it ends in RCE. Tab 1, command injection: the ping tool glues your input into a shell line, so 8.8.8.8; whoami runs a second command — you're now www-data on their box; the reverse-shell preset hands you a live terminal (this is literally Day 2's "first shell", reached through the app). Watch the assembled shell line and the injected part in red. Fix: don't call a shell — pass input as a single argument (execFile), so ; is just a bad hostname. Tab 2, path traversal: the file downloader reads /var/www/reports/<you>, and ../../../../etc/passwd climbs out of the folder to any file on disk — watch the resolved path. Fix: strip the path, keep the filename. Same root cause as always: input treated as instructions (a command, a path) instead of data.

Injection · into the browser this time

XSS: your comment becomes everyone else's code

Same disease, different tier: SQLi injects into the database; XSS injects into the PAGE. One-line primer: a session cookie is the token that proves you're logged in — steal it and you ARE that user, no password. Drive it: post a normal comment (renders as text), then post <script>steal(document.cookie)</script>. Because the app writes your comment into the page without encoding it, the victim's browser RUNS it — watch the victim's cookie land in the attacker console. Note the comment itself looks EMPTY in the feed: a script tag renders as nothing, which is exactly what stored XSS looks like to a normal visitor. Then hit the second payload — same theft with <img src=x onerror=…>, no <script> tag at all — and say the line: blocking the word "script" is not a fix, because there are a hundred other tags that run code. Stored (saved for every viewer) vs reflected (in a crafted link) in one line. Then flip "encode output on render": the same script now shows up as visible <script> text — inert. Land: the fix is to treat input as data to DISPLAY, never as HTML to execute.

Riding your session · the confused deputy

CSRF: another site spends your login for you

This is why the session-cookie slide mattered. The browser automatically attaches your cookie to any request aimed at that site — even a request fired by a different, malicious page. Drive it: victim is logged into the bank in one tab; on evil.com they click an innocent "claim your gift" button that secretly POSTs a transfer to the bank. The browser helpfully attaches the bank cookie, the bank sees a valid session and obeys — money gone, victim never touched the bank tab. Point at the highlighted "auto-attached by YOUR browser" line; that's the whole bug. Note the spine bends slightly here: it's not "input as code", it's the app trusting that a cookied request was intended by the user — a confused deputy. Fix: a CSRF token the real form carries and evil.com can't read (same-origin policy), so the forgery is missing it and bounces. Mention SameSite cookies as the modern default defence.

Broken access control · the lazy check

IDOR: the app checks what you asked for, not who you are

You're logged in as a real user — the app authenticated you. It just never checks that invoice #1042 is yours. Add one to the id and you're reading someone else's. No exploit, no payload — just a number you changed in the address bar.
Deliberately light — the mechanism is simple, so it's a small driven demo plus a sentence, not a heavy sandbox (per the guide's filter). You are AUTHENTICATED (you logged in) but not AUTHORISED per-object: the server fetches invoice #id and returns it without asking "does this id belong to the caller?". Drive the id up and down and watch other people's data appear. This is the #1 web vuln by prevalence (OWASP A01). The fix is one line: check ownership on every object, every request — server-side. Ties straight into the defender slide next.

Broken authentication · the front door

Sometimes you don't break the app — you just walk in

Credential stuffing

Replay the breach dumps from Day 2 — reused passwords still work.

Beaten by: unique passwords + MFA

No rate limit

Guess a password millions of times; nothing slows you down.

Beaten by: lockout + throttling

Weak session tokens

Predictable or never-expiring cookies you can guess or reuse.

Beaten by: random, short-lived tokens

Password reset abuse

Guessable reset tokens or leaky "forgot password" flows.

Beaten by: signed, expiring links
Authentication is who you are; authorisation (the last slide) is what you're allowed. Apps break both — and the login page is where Day 2's stolen passwords cash out.
A concept slide — these are mostly common-sense-once-stated, so it's cards, not a sandbox. The point is breadth + the bridge back to Day 2: the whole credential economy from the foothold day ends HERE, at a login form with no rate-limit. Draw the auth vs authz distinction explicitly — it's a classic exam/interview line and sets up why IDOR (authz) is separate from stuffing (authn). Keep it fast.

The other side · how every one of these dies

The whole day collapses to four defensive habits

Never trust input

Validate on the server, allow-list what's valid. Client checks are UX, not security.

Kills: tampering, bad data

Parameterise queries

Send input as bound data, never glued into a command string.

Kills: SQL injection

Encode on output

When you write user input into a page, escape it — display it, don't execute it.

Kills: XSS

Authorise every request

Check ownership and role on every object, every time — server-side.

Kills: IDOR, broken access
One sentence for the week: decide trust on the server, keep data and code separate, and check authorisation on every action.
And a WAF isn't a fifth habit. A web application firewall pattern-matches known payloads at the door — useful defence-in-depth, but a net, not a fix: encodings and novel tricks slip past it. It buys time; the four habits close the hole.
The payoff and the bridge to Day 5. Don't present these as new — each one is the direct inverse of an attack they just drove, so name the attack for each fix. The meta-lesson: you don't memorise a hundred vulns, you internalise four habits, all versions of "the app must decide trust itself, on the server." This is the seed of the defender day. End on the one-sentence summary.

The other side · you left tracks

Every attack you ran wrote a line in someone's log

The bridge to Day 5, and the counterpart to Day 2's traces slide — but the lesson flips. On Day 2, passive recon was invisible. Today there is no passive: every web attack touches the server, so almost everything screams — a WAF catches the SQLi signature, EDR catches the shell your command injection spawned, Identity catches the impossible-travel on the hijacked cookie. Replay them and watch the alerts stack up. Then land the ONE exception: walking the invoice ids (IDOR) fires nothing — every request is a valid, authenticated 200, indistinguishable from normal use. That's why broken access control is the most-exploited and most-missed bug, and it's exactly the needle they'll hunt on Thursday: not the loud alert, but the anomaly hiding in legitimate traffic.

Before you touch anything real · rules of engagement

Do this only where you're allowed — and there are plenty of places

The line you do not cross

Everything you drove today against a system you don't own, without written permission, is a crime — under Saudi Arabia's Anti-Cyber Crime Law that means fines and prison, whether or not you caused damage. A simulation is practice; a live site is someone's property. Curiosity is not authorisation.

Rule: no scope in writing → you don't touch it.

Where it's not only legal but encouraged

Deliberately-vulnerable apps built for you to attack, on your own machine or their sandbox:

OWASP Juice Shop — a whole vulnerable shop, runs locally.
PortSwigger Web Security Academy — free, guided labs.
DVWA · bWAPP · HackTheBox / TryHackMe — sanctioned targets.
Bug-bounty programs — real sites that invite testing, within scope.
The real toolkit (for authorised work): Burp Suite & OWASP ZAP — the intercepting proxy behind today's "edit the request"; ffuf / gobuster — the content-discovery behind the status-code probe; sqlmap — automates the SQL injection you drove by hand. Same moves, real tools, legal targets.
The ethics slide Day 4 was missing — and it's mandatory before a room of students who now know how to do real damage. Lead with the boundary, hard: unauthorised = criminal under the Saudi Anti-Cyber Crime Law, damage or not; "I was just curious / just looking" is not a defence. Then pivot fast to the empowering half so it doesn't read as pure warning — there is a huge legal playground. Have them install Juice Shop or open a PortSwigger lab and actually redo today's attacks for real (they're online). Name the real tools so the widgets connect to industry reality: Burp = the trust-boundary intercept, ffuf = the status-code probe, sqlmap = the SQLi widget automated. This is also the defender's mindset seeping in before Thursday.
