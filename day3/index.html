Act 1 · first principles · the definition

A network is machines that agreed to talk

Nodes the things

Anything with a network address: laptops, phones, servers, printers, cameras — and the switches and routers themselves.

Links the path

The wire or the radio that physically carries the bits: Ethernet cable, fibre, Wi‑Fi. A link moves bits; it doesn't understand them.

Protocols the rules

An agreed set of rules for how to ask, answer, and address. Without a shared protocol, two connected machines just exchange noise.

Scale lan · wan · internet

LAN = one site. WAN = sites joined across distance. The internet = every network agreeing on one protocol family.

The analogy for the whole of Act 1: a road system. Nodes are buildings, links are roads, and protocols are the traffic law everyone agreed to obey. Break the law here and you don't get a ticket — you simply don't arrive.
Slide one of the foundations block, and deliberately the most basic thing in the deck — nothing later works without it. Define a network out loud in one sentence: two or more devices connected by something that carries bits, following shared rules. Then walk the zoom-out: (1) two machines and a link is already a network — demystify the word; (2) an office LAN is the same thing with a switch in the middle so everyone doesn't need a cable to everyone (n machines would need n² cables — the switch is what makes it practical) plus a router as the way out; (3) the internet isn't a thing you connect to, it's every one of those networks agreeing on the same protocol family — a network of networks. Land the three ingredients (nodes, links, rules) and the road analogy; you'll reuse the analogy on the next three slides. Ask the room: how many nodes are on the café Wi‑Fi right now? ~90s.

Act 1 · first principles · the three addresses

Three addresses, three jobs: MAC, IP and port

MAC which device

A 48-bit ID burned into the network card at the factory. Only meaningful on the local wire — a router strips it and writes a fresh one every hop.

Analogy: your ID card — yours for life, unchanged when you move.

IP which machine, where

A logical address the network assigns you, like 192.168.1.50. It survives the whole trip end-to-end — it's what routers steer by.

Analogy: your street address — move office, get a new one.

Port which program

A number from 1–65,535 picking one program on that machine — 443 the web server, 22 SSH. Many conversations, one machine.

Analogy: the department at that address — Sales vs Payroll.
One sentence to keep: the MAC gets it to the next device on this wire, the IP to the right machine anywhere on earth, the port to the right program on it. Every attack today targets one of the three.
The single most load-bearing slide of the day — if they leave with only one thing, make it this. Teach it strictly as three jobs, not three formats: MAC = which device (factory-fixed, local-only, rewritten every hop), IP = which machine and where (assigned, end-to-end, routable), port = which program (1–65535, picks the service). Use the ID-card / street-address / department analogy and repeat it verbatim — it's the one they'll quote back. Walk the three pictures left to right and read the real value under each: the ID card is a1:b2:c3:44:55:66, the house on that street is 192.168.1.50, the desk inside it is :443 — analogy, then the actual thing, every time. Push the house analogy one step: the street sign is the network half, the number on the door is the host half (that's the next slide but one). Close on the line under the panels — one message carries all three at once — and promise the picture of how they're wrapped together: that's exactly what the encapsulation player animates shortly. Then map the day forward: ARP spoofing lies about MAC, subnetting and NAT are about IP reach, and port scanning hunts programs. Check for understanding before moving on — ask which of the three changes when you carry your laptop to a café (the IP). ~2 min; this one is worth the time. It has to land before the next slide, which is built entirely on MAC vs IP.

Act 1 · first principles · the two boxes

Switch vs router — inside a network vs between

Switch layer 2 · inside

Learns which MAC address sits on which of its ports, then sends each frame down only that one port. It never looks at IP addresses and doesn't need one itself.

Analogy: the mail room inside a building — moves post office to office, never leaves the building.

Router layer 3 · between

Joins different networks. Reads the destination IP, decides the next hop, and hands the packet on. It's your default gateway — and where the firewall and NAT live.

Analogy: the post office — everything leaving the building goes through it, and it keeps a record.
Why an attacker cares: the switch is what stops you overhearing your neighbours — Act 2 gets round it by lying. The router is the chokepoint every outbound packet must cross, so it's where defenders watch and cut you off. (Your home “router” is really four boxes in one: modem + router + switch + Wi‑Fi.)
The second foundation, and the one adults most often have never had explained. Beats: (1) a switch works inside one network using MAC addresses — it learns which machine is on which port and delivers only there; that isolation is a security property, and it's exactly what ARP spoofing defeats later today; (2) a router works between networks using IP — it is the border, the default gateway, and the place NAT and the firewall live; (3) the mail-room / post-office analogy — say it once, it sticks. Mention the hub in passing if asked: the obsolete ancestor that copied every frame to every port, which is why sniffing used to be trivial. Then the practical note: a home "router" is a modem + router + switch + access point in one box, which is why the word confuses everyone. Do NOT go into routing tables — they only need "it decides the next hop". ~90s.

Act 1 · first principles · the model

The OSI model: one big job, split into seven layers

A protocol is an agreed set of rules two machines follow so they understand each other. There are hundreds — so the OSI model sorts them into seven layers, each solving one problem and trusting the layer below to do its own. It's a map, not a machine.
7Application What the program actually wants — “fetch this page”, “log me in”.
6Presentation Put it in a form both sides read the same way — formats, compression, encryption.
5Session Open, hold and close the conversation — who is talking to whom, and for how long.
4Transport Cut it into pieces, deliver them to the right program (the port), and make sure none went missing.
3Network Address it end-to-end (the IP) and choose a route across the world, hop by hop.
2Data link Hand it to the next device on this wire (the MAC), and check it arrived undamaged.
1Physical The bits themselves — voltage, light, radio. Cables, fibre, Wi‑Fi.
Notice layers 4, 3 and 2: they are exactly the port, the IP and the MAC — and layers 3 and 2 are exactly the router and the switch. That's not a coincidence; the addresses and the boxes are the layers. Next: watch a real message get wrapped, layer by layer.
The model, defined before it's used. Two definitions, slowly: protocol = agreed rules (call back to the traffic law from the network slide); OSI model = a seven-layer map that splits the job so each layer solves one problem and trusts the one below — the reason you can swap Wi‑Fi for a cable without rewriting the browser. Read the layers downward (7→1) as "the message getting closer to the wire", then say plainly that layers 4-3-2 are the port, IP and MAC they just learned — that's the sentence that makes the model click. Two honest caveats: (1) it is a teaching model, not code — the real internet uses a four-layer TCP/IP stack that folds 5-7 into "the application", which is the slide after next; (2) people say "layer 7 attack" or "layer 2 attack" all day in this industry, which is the practical reason to know the numbers. Mnemonic if you want one, top down: All People Seem To Need Data Processing. ~2 min, then straight into the player.

Act 1 · the 7-layer model, in motion

Watch it happen: each layer wraps the message in its own header

The seven layers you just defined, now in motion — this is the picture, the last slide was the map. Press Play. The SAME message goes DOWN 7 layers on the sender, each layer wrapping the value in its own header (encapsulation), then UP 7 on the receiver, each header stripped in reverse (decapsulation). Watch the PDU grow: L7 the data → L6 encrypts it (TLS) → L5 session → L4 adds a TCP header (ports + sequence) making a SEGMENT → L3 adds an IP header (the addresses) making a PACKET → L2 wraps a FRAME (MAC addresses) + an FCS error-check → L1 turns the whole thing into BITS on the wire. The receiver undoes it in exact reverse order. Point back at the three addresses slide as the headers appear: the TCP header carries the PORT, the IP header the IP, the frame the MAC — the nested picture they saw drawn is now animating. One caveat to repeat: each header is data ABOUT the data, read only by its peer layer on the other side. Tie it forward hard: every attack today abuses one of these layers (ARP at L2, IP/subnets at L3, ports/TCP at L4, DNS/HTTP/TLS at L7), and Wireshark — later in this same Act — just opens these exact headers on real traffic.

Act 1 · layer 2 · the local wire

On the wire, traffic rides in frames — and one question has no answer yet

A laptop on the wire
IP 192.168.1.50  ·  MAC a1:b2:c3:44:55:66
Both addresses, on one machine — as defined earlier. Now the practical problem: to actually put a frame on this wire, which of the two do you need?

MAC address recall

A 48-bit ID fixed to the network card, like a1:b2:c3:44:55:66. It only means anything on this local wire — routers strip it and write a fresh one each hop.

IP = the street address · MAC = the ID card.

Frame wraps packet nesting

Day 1's onion: the IP packet (with IP addresses) is wrapped in a frame (with MAC addresses) to cross one hop of wire. New frame each hop.

To send a frame you need the destination's MAC.

Broadcast vs unicast reach

Unicast = a frame to one MAC. Broadcast = destination ff:ff:ff:ff:ff:ff — every device on the wire receives it.

Broadcast is how you ask a question of the whole room.
The gap: to put a frame on the wire you need the destination's MAC — but you usually only know its IP. The protocol that bridges that gap is ARP, and it's the toy on the next slide. Watch how it asks — because that's also its weakness.
Foundation for ARP and, later, MITM. Three beats: (1) a quick recall of the two addresses — don't re-teach them, just re-anchor which is local (MAC) and which is end-to-end (IP); (2) frame-wraps-packet is the encapsulation player named at layer 2 — a fresh frame every hop; (3) broadcast (all-ones MAC) vs unicast, because the ARP request is a broadcast. End on the gap — you know the IP, need the MAC — which is exactly the problem ARP solves next. ~75s.

Act 1 · layer 2 · ARP on the local wire

ARP: the question that turns an IP into a MAC

The first real mechanism of the day, and the bottom rung of the stack. Restate the gap in one line — you know the destination's IP, you need its MAC to put a frame on this wire — then let the player answer it. Drive the player: (0) you know .5's IP but not its MAC; (1) you BROADCAST "who has .5?" to everyone — dst MAC ff:ff:ff:ff:ff:ff; (2) only .5 replies with its MAC, the rest ignore it; (3) you cache the mapping; (4) now the real data frame goes straight to .5's MAC. The two things to land: (a) IP vs MAC — who vs where-on-this-wire; (b) the trapdoor — ARP is an unauthenticated broadcast: ANY machine can shout "that's me." Hold that; in Act 2 we become the liar (ARP spoofing). Real-world scale: a busy LAN resolves thousands of these a minute, all cached for ~seconds.

Act 1 · layer 3 · an address, up close

Open up an IP address: it's four numbers, and really two things

192.168.1network · which wire .50host · which machine
Like a street name plus a house number: the network part says which wire you're on, the host part says which machine on it.

32 on/off switches

Four numbers, each 0–255 — that's 8 bits apiece, 32 bits in total. That's all an IPv4 address is.

e.g. 192.168.1.50

Network + host

The address splits into a left half (the wire) and a right half (the machine). Same left half = same local network.

So: .10 and .50 here are neighbours.

The mask draws the line

The subnet mask (/24) is just where the split falls. Move it and machines fall in or out of “your wire.”

/24 = first 24 bits are the network.

Private vs public

192.168.x, 10.x, 172.16–31.x are private — reused inside every office. Everything else is public.

Private can't be reached from the internet directly.
Why the line matters: same network half = neighbours, and the switch delivers between you directly. Different network half = the router has to carry it — and a router can log it, filter it, or refuse. The next slide is a toy: drag the mask and watch machines fall to the far side of the router.
Not the definition of an IP — they have that from the three-addresses slide — this is the anatomy of one. Land three things and move on: (1) an IP is 4 octets = 32 bits, nothing mystical; (2) it has a network half and a host half, and the mask is just the movable boundary between them; (3) private ranges are reused everywhere, which is why the internet can't route to them (sets up NAT). Then connect it straight back to the switch/router slide: which side of the line a machine falls on decides which of the two boxes carries your traffic — and that is the whole idea of segmentation. Keep it ~90s; the next slide lets them feel the mask by moving it.

Act 1 · layer 3 · addressing & reach

Two halves of an address — and the wall called NAT

The foundation everything else stands on — do this before ARP. An IP address isn't one number, it's two: a network part and a host part, and the subnet mask is what says where the split falls. Walk the bits: at /24 the first 24 bits are the network, so every 192.168.1.x is on the same wire and you reach them directly — with the ARP you just watched. Slide to /25 and /26 and watch db01 and fileserver fall OUT of your subnet — still reachable, but only through the router, which can log, filter or refuse. That is segmentation, and it's the single most effective defence against the lateral movement we do in Act 2: it shrinks the blast radius of one compromised box. Say it in the vocabulary they now have: every machine you push out of the subnet is one the switch can no longer reach directly, so the router gets a say. Then flip to Attacker on the internet for the big land: 192.168.x.x is a private range — millions of networks use it, so the internet won't route to it. The router does NAT, which lets the office out and matches up the replies, but nothing outside can start a conversation in. Ask the room the question this answers: "if the office is unreachable, how did we get in on Day 2?" — you didn't knock, you got invited, by phishing. Every attack today only works because you're already on the wire.

Act 1 · layer 3 · routing · how data actually moves

A message travels as packets, not one stream

The mental model for the whole network. Press Send: "HELLO" is SPLIT into 5 packets, each carrying its own header (from-IP, to-IP, sequence number, TTL). Packets HOP router-to-router — laptop → home router → ISP → a backbone router → server — and DIFFERENT packets take DIFFERENT paths (top vs bottom). They ARRIVE OUT OF ORDER (watch the reassembly strip: 2, 4, 3, 5, 1) and the server REORDERS them by sequence number to recover "HELLO". Point at the inspector: TTL drops by one each hop — that's the "hop limit" that stops packets looping forever, and it's exactly what traceroute abuses in the discovery slide shortly. Then hit "Cut the top link" and Send again: every packet REROUTES through the bottom path — the network routes around damage, which is literally why it was built. Land the picture: addressed packets, independent paths, reassembly by sequence — the header that says where is the IP header from the layer stack you just saw.

Act 1 · layer 3 · discovery · the quiet plumbing

Before you attack a host, you have to find it

DHCP your IP

Broadcast: "anyone got an address for me?" The reply hands you an IP, mask, gateway and DNS.

Trapdoor: trust-by-answer, like ARP — a rogue server names itself your gateway.

ICMP · ping alive?

Not a port, not a service — a control message. Echo request out, echo reply back.

But: many hosts drop ICMP on purpose. Silent is not dead.

Ping sweep the map

Ping every address in the subnet and list who answers.

Step 0 of every scan: hosts first, then ports — that's the next slide.

ARP scan on-wire

On your own subnet, ask by ARP. A host can ignore ping — it can't ignore ARP and still work.

So: ARP finds what ping misses.

traceroute the path

Packets with a deliberately short lifespan (TTL) — each router in turn reports itself.

Reveals: the hops between you and the target — and where the firewalls sit.
None of this is an exploit. Every one of these is a protocol doing exactly what it was designed to do — which is precisely why discovery is so hard to block.
A short, brisk slide — cards, not a toy, because each of these is a one-sentence idea. It sits here because discovery logically precedes the port scan: first which machines exist, then which doors each one has. Beats to land: (1) DHCP answers "where did my IP even come from" and completes the addressing story from two slides back — and note the rogue-DHCP trapdoor, the exact same trust-by-answer flaw as ARP and DNS; that pattern repeating three times is the real lesson of Act 1. (2) ping/ICMP — worth saying explicitly that ICMP is not TCP or UDP and has no ports; it's the network's own signalling. (3) ping sweep — the mental model of hosts-then-ports. (4) ARP scan — the nice attacker detail: a host can firewall off ICMP but cannot refuse ARP and still function. (5) traceroute — the TTL trick is genuinely clever, worth 20 seconds. Close on the callout: discovery abuses nothing, so defenders can't simply "patch" it — they can only segment and monitor.

Act 1 · layer 4 · ports, up close

Ports, up close — and the one word that matters: listening

22 SSH 80 HTTP 443 HTTPS 445 SMB 3389 RDP
One IP, but up to 65,535 ports. The port number is how the machine knows which program a packet is meant for.

Why ports exist recall

A server runs a web server and a database and SSH at once. They share one IP — the port number is what keeps their traffic apart.

IP finds the machine; port finds the program on it.

Listening = a door that's open

A program that's running and waiting for connections is listening on its port. A listening port = an open door. No program there = closed.

Open means something is behind it to talk to — or attack.

Numbers you'll keep seeing

Services sit on well-known ports by convention: 22 SSH, 80/443 web, 445 file shares, 3389 remote desktop.

See a port → you can guess the service.
A port scan just knocks on every door and notes which open. Each open door is a running service — and each service is its own way in. The next slide is that scanner; press it and read the doors.
Foundation for the port scan and, really, for all of Act 2's targeting. Land: (1) one IP hosts many programs, and the port number multiplexes them — that's the whole reason ports exist; (2) “listening” is the key word — an open port is a program waiting, a door with something behind it; (3) well-known ports let you read a scan at a glance. Don't drill the numbers; they'll meet them live on the next slide and again in the port-scan mapping (SSH→login, SMB/RDP→lateral). ~70s.

Act 1 · layer 4 · ports & services

One IP, many doors — a port scan finds the open ones

An open port is a running service — a door with something behind it. Finding them is the attacker's first move once inside; each service maps to its own attack.
Now that you can reach a host (ARP got you its MAC), what can you talk to? A machine has one IP but 65,535 ports; a port that's listening = a running service = a door. Press Scan: the sweep probes every common port and each resolves open / closed / filtered. Land the mapping — every open port is a specific attack surface: 22 SSH → credential attack, 445 SMB & 3389 RDP → lateral movement (Act 2), 3306 MySQL → the data itself, 80/443 → the web app (Day 4). Then hit Toggle firewall: the sensitive internal services go filtered — the probe is dropped, you can't even tell what's there. That's the defender's lever: fewer open doors = smaller attack surface. This is nmap at toy scale; a real scan sweeps all 65,535 ports and fingerprints versions to match known CVEs.

Act 1 · layer 4 · connections · first principles

Two ways to send data: with a handshake, or without

SYN let's start ACK got it RST go away
TCP's “handshake” is nothing but these tiny flag bits in the header, sent back and forth: SYN → SYN-ACK → ACK, then data.

TCP reliable

Sets up a connection first, numbers every byte, re-sends anything lost, keeps order. Costs a little time; buys certainty.

Used by: the web, SSH, RDP, file shares.

UDP fast & loose

No setup, no memory, no re-send. Packets just fly; a lost one is simply gone. Less overhead, less certainty.

Used by: DNS lookups, voice, video, games.

Flags = control bits SYN·ACK·RST

A handful of on/off bits steer a TCP connection. SYN opens, ACK confirms, RST refuses/aborts. That's the whole handshake.

State = both sides remembering where they are.
The same handshake is the attacker's scanning trick: send only the first SYN, read the reply, and bail before finishing. The next toy plays all three — TCP, UDP, and that half-open scan.
Foundation for the tcp/udp toy and the SYN scan. Beats: (1) reliable vs unreliable is a genuine trade-off, not good vs bad — match protocol to job; (2) “connection” means both sides hold state (remember the conversation), which UDP doesn't; (3) flags are just control bits, and the 3-way handshake is literally SYN/SYN-ACK/ACK. Plant the hook: the scanner abuses the handshake by never finishing it. Keep sequence-numbers to one phrase (“numbers every byte”) — the toy shows it. ~75s.

Act 1 · layer 4 · connections

TCP shakes hands before it talks — UDP just fires

How do two machines actually hold a conversation? Switch between the three tabs and Play each. TCP: the 3-way handshake — SYN, SYN-ACK, ACK — builds a connection BEFORE any data; watch both sides walk CLOSED/LISTEN → ESTABLISHED. The payoff line: three packets before a single byte, and that cost buys reliability (ordering, retransmits). SSH, HTTP(S), RDP all ride TCP. UDP: no handshake, no state — packets just fly and a lost one is simply gone; great for DNS, voice, video. SYN scan: the attacker's trick — send only the SYN, read the reply (SYN-ACK = open, RST = closed), then send RST to bail before completing. That half-open scan is exactly how the port sweep two slides back found the doors — fast and quiet. Ties the connection mechanism to the recon they saw.

Act 1 · layer 7 · names → addresses · first principles

A web name is read right-to-left — like a postal address, biggest last

wwwhost. majalthe org. sacountry · TLD.  · the root
Machines route to numbers, but people remember names. DNS turns majal.sa into an IP — by walking this tree.

Nobody knows every name

No single server holds the whole internet. It's a tree of referrals: the root points to the country (.sa), which points to the org's own server.

Each level only knows who to ask next.

Your resolver does the walk

You don't climb the tree yourself — a helper called the resolver asks each level for you and hands back the final IP.

One question in, one answer out.

…and remembers it

The resolver caches the answer for a while (its TTL), so the next lookup of the same name is instant — no walk.

Billions of lookups/sec ride on this caching.
Here's the catch you'll weaponise later: DNS believes whoever answers first. Forge a reply and the victim happily connects to your server. Watch the walk — and that gap — on the next slide.
Foundation for the DNS resolver toy. Land: (1) read the name right-to-left, biggest scope last, with an invisible root dot — demystifies “what is a TLD”; (2) it's a hierarchy of referrals, not one magic lookup — nobody holds everything; (3) the resolver does the recursion and caches by TTL. End on trust-by-answer, the same flaw as ARP/DHCP — that rhyme (three protocols, same weakness) is the real spine of Act 1. The toy animates the walk and the cache hit. ~75s.

Act 1 · layer 7 · names → addresses

DNS: the internet's phonebook (and who it trusts)

Machines route to IPs, but humans remember names — DNS bridges the two. Press Resolve and watch the recursive walk: your resolver asks a root server (→ "ask .sa"), then the .sa TLD (→ "ask ns1.majal.sa"), then the authoritative server, which finally returns the IP. The resolver caches it — hit "Resolve again" to see the instant cache hit (no walk). Land two points: (1) it's a hierarchy of referrals, not one lookup; (2) the security gap that rhymes with ARP — DNS is trust-by-answer: whoever replies first is believed, so a forged reply (cache poisoning / spoofing) silently sends the victim to the attacker's server. Real scale: billions of queries/sec, cached at every layer. We won't build the spoof here — the ARP version in Act 2 makes the same point on the wire.

Before the tool: how you actually read a captured packet

The raw packet in hex and text. If the app didn't encrypt, the text column is plainly readable — headers, form fields, and all.

The point of the next slide: a packet isn't magic — it's these nested labels, and anyone on the wire can read the unencrypted ones. One real login, every layer, the password in the clear — then the same login over HTTPS, sealed.
Orientation so nobody is lost when the Wireshark UI appears. Just teach the three panes and their top-to-bottom logic: list (pick a packet) → tree (layers unwrapped, one per line — tie straight back to Day 1's encapsulation) → hex/text (the actual bytes; readable if unencrypted). Set the expectation for the marquee: they'll see the TCP handshake from two slides ago, then a cleartext password, then watch HTTPS hide it. ~60s — it's a map, not a lecture.

Act 1 · every layer at once · open a real packet

Wireshark: one login, every layer you learned

The payoff of Act 1 — the encapsulation stepper that opened the Act promised these headers on real traffic, and here they are (a reconstructed capture of one login). Walk the packet list: notice packets 1–3 are the TCP handshake from two slides ago. Click packet 4 (POST /login) and open the dissection tree: it is literally every layer they learned as one row each — Ethernet (the MAC addresses ARP resolved), IP (the addresses), TCP (the ports that pick the service), then HTTP. Now flip to HTTPS :443 and click the Application Data packet — same login, but TLS has sealed it; the bytes are opaque ciphertext, no password to see. Two lands: (1) a packet is just these nested headers you can read; (2) HTTP exposes everything to anyone on the wire, HTTPS doesn't — which is exactly the attack we run next. Bridge to Act 2: "so how does an attacker get onto the wire to read HTTP? Watch."

Act 1 · layer 7 · the padlock · first principles

HTTPS solves two problems — and the second is the hard one

Problem 1 · secrecy

Scramble the data so a sniffer sees only ciphertext. That's encryption — Day 1's key exchange, and honestly the easy half.

Anyone can encrypt. That's not enough.

Problem 2 · identity

Be sure you scrambled it to the real majal.sa, not an impostor in the middle. Encrypting to the wrong server is worse than not encrypting.

This is the half a certificate solves.

The certificate an ID card

A signed card the server presents: its name, its public key, and a signature vouching that the two belong together.

Name + key, notarised.
Who does the vouching? A Certificate Authority (CA) your browser already trusts. Anyone can type the name “majal.sa” into a certificate — but only a CA's signature makes it believable, and you can't forge that. A certificate signed by nobody (self-signed) is the tell of an impostor.
Foundation for the TLS/cert toy and, downstream, the HTTPS MITM. The one idea students miss: encryption ≠ authentication. Encryption is easy; knowing who you encrypted to is the hard part, and that's the certificate's whole job — it binds a public key to a name, and a CA signature makes the binding trustworthy. Say plainly: anyone can claim a name, nobody but a CA can sign for it, self-signed = unvouched. That single asymmetry is what makes the next slide's man-in-the-middle fail — and why the only way past it is tricking the human. ~80s.

Act 1 · layer 7 · the lock, opened up

Why HTTPS beats you: certificates, not just encryption

The slide that answers the question the Wireshark slide raised and never explained: why is HTTPS opaque? Play it in Just the server first. ClientHello (nothing secret yet, all in the clear) → ServerHello + Certificate → the browser verifies it → key exchange → sealed Application Data. Land the one idea students usually miss: encryption is the easy half — knowing WHO you encrypted to is the hard half. Anyone can encrypt; the certificate is what binds a public key to the name "majal.sa", and a Certificate Authority's signature is what makes that binding believable. Day 1 already built the key exchange (Diffie–Hellman) — point at that step and say "this is that, running for real". Then switch to Attacker in the middle: you're ARP-spoofed into the path from the MITM slide, so you must terminate TLS yourself, which means handing alice a certificate for majal.sa. You can type the name, but you cannot forge a CA signature — so you self-sign, and the browser catches it instantly and throws NET::ERR_CERT_AUTHORITY_INVALID. Now make someone in the room click "Proceed anyway." Watch the password appear in your pane. The final land, and the best line of the day: TLS did not fail — alice overrode it. The last defence was a human decision, which is exactly Day 2's territory. This is also why browsers made that warning so ugly and hard to bypass, and why a cert warning on a public Wi-Fi network should end the session.

Act 1 · back down to layer 1 · the wireless edge

Wi-Fi is a shared room, not a private wire

Radio reaches everyone

A cable carries your packets to one place. Wi-Fi broadcasts them into the air, where every device in range can hear them.

So: privacy on Wi-Fi is done by encryption, not by the wire.

WPA2 / WPA3 — the password

The network key encrypts the radio link, so neighbours hear noise instead of your traffic.

But: it protects the air only — everyone who knows the café password is inside it with you.

Open networks

"Free Airport WiFi" with no password means no encryption at all. Anyone nearby with a laptop can read what isn't otherwise protected.

Your last defence: HTTPS, on every single site.

The evil twin

An attacker runs an access point using the same network name. Your phone prefers the stronger signal — and joins it automatically, without asking.

Result: all your traffic now flows through them.
The lesson isn't "avoid public Wi-Fi" — it's that the network is never what's protecting you. End-to-end encryption is. That's why the padlock matters, and why a certificate warning on a café network should end the session.
Capstone of Act 1's "language" block, right before we go inside — it closes the loop from the TLS slide (E2E encryption + the human click-through) and sets up Act 2's man-in-the-middle. Beats: (1) a wire delivers to one socket, radio delivers to everyone in range — so on Wi-Fi, privacy has to come from encryption; that re-frames the WPA password not as "permission to join" but as "the key that scrambles the air". (2) WPA2/WPA3 secures the radio hop only — on a shared café password, everyone who has it is inside the encrypted zone with you; not a private tunnel. (3) An open network has none of that: traffic is literally readable by anyone with a cheap adapter, which is why HTTPS-everywhere stopped being optional. (4) The evil twin is the memorable one — devices auto-join the strongest signal with a remembered name, so an attacker just names their AP "Starbucks WiFi" and waits. Ask the room how many phones would join automatically right now. Land the callout hard: the defence isn't avoiding networks, it's assuming every network is hostile and relying on end-to-end encryption — which is exactly what Act 2 proves in a moment, when we sit in the middle of a network and try (and fail) to read HTTPS.

Act 2 · staying in touch · first principles

A firewall guards the door — and direction is everything

✕ INBOUNDinternet → office: denied by default. Nobody dials in.
✓ OUTBOUNDoffice → internet: allowed. Staff must browse, email, update.
A firewall is a guard that allows or denies traffic by rule — mostly by port and direction. It's stateful: replies to your own outbound requests are let back in.

What a shell is

A shell is a remote command line on the victim — the thing Day 2 landed. To use it, you need a network path between you and it.

The firewall decides whether that path can exist.

Bind = you dial IN

The victim opens a port and waits; you connect inward. Obvious — and doomed, because inbound is the one direction the firewall blocks.

Needs inbound. Dead on arrival.

Reverse = victim dials OUT

Flip the arrow: the victim connects out to you. The firewall waves it through, because outbound is how everyone works.

This is how nearly every real foothold phones home.
The whole trick is that one flip. A firewall guards the entrance, not the exit — so make the victim call out, and dress it up as ordinary web traffic on 443. Run all three on the next slide.
The missing foundation the C2 toy assumes — teach it before, not during. Two halves: (1) a firewall filters by port and direction, and the asymmetry is the whole lesson — inbound denied, outbound allowed, stateful so your own replies return; anchor it to the port-scan firewall toggle they already saw. (2) a shell needs a path, and bind (dial in, blocked) vs reverse (dial out, allowed) is just which end opens the connection. Land the one-liner — “guards the door, not the exit” — then the toy shows bind die, reverse work, and C2 hide on 443. ~85s; this is load-bearing.

Act 2 · staying in touch · command & control

Your shell has to phone home

A firewall guards the door, not the exit. That asymmetry is why virtually every real implant is built to call out rather than be called.
The plumbing question Act 2 otherwise skips: you have a shell on web01 — but how are you still talking to it? Run all three. Bind shell: web01 listens on 4444 and you dial in — the obvious design, and it dies instantly, because inbound-deny is the one rule every edge firewall has (tie back to the firewall toggle on the port scan slide). Reverse shell: flip the arrow — web01 dials out to you, and the firewall waves it through, because outbound is how staff get work done. That inversion is the whole insight, and it's how nearly every real foothold works; Day 2's payload did exactly this. But 4444 outbound is odd-looking, so a defender watching egress can spot it. C2 over HTTPS: beacon out on 443 wrapped in TLS, at intervals. The firewall must allow 443, and the content is encrypted — note the irony out loud: the same TLS that protected alice two slides ago is now hiding the attacker. The tell is not the content but the rhythm — human browsing is bursty and irregular, a beacon is metronomic, and that timing signature is exactly what a defender hunts for on Thursday. Real tools: Cobalt Strike, Sliver, Mythic; the "beacon" name comes from this behaviour.

Act 2 · sniff the wire · first principles

Why you can't just “listen” — and how one lie fixes that

A switch is not a megaphone

A switch sends each frame only to the port of its real destination MAC. So on a switched network you don't normally see anyone else's traffic — even on the same wire.

That's why simply sniffing gets you nothing.

Everything leaves via the gateway

Any traffic bound for another network goes to the gateway (the router) first. So the victim → gateway path carries all the interesting stuff — logins, browsing, the lot.

Own that path and you own the traffic.

ARP takes no proof recall

Remember the layer-2 slides: ARP believes any machine that claims an IP. So lie to both sides — tell the victim “I'm the gateway,” tell the gateway “I'm the victim.”

Both cache your MAC. Traffic now bends through you.
That detour is a man-in-the-middle. The switch was doing its job perfectly — you didn't break it, you fed it a lie about who's where. Spoof, then read the victim's login, on the next slide.
Foundation for the MITM toy — it removes the two “wait, why does this work?” gaps. (1) A switch isolates traffic by MAC, so sniffing alone fails — this is the thing beginners don't know and it's why an attack is even needed. (2) All off-subnet traffic funnels through the gateway, so impersonating the gateway captures everything. (3) Tie back hard to the ARP primer: ARP has no authentication, so poisoning both victim and gateway reroutes the path through you. Then the toy: normal = empty capture, spoof = the path bends and the cleartext password appears, HTTPS = still relayed but sealed. ~75s.

Act 2 · sniff the wire · man-in-the-middle

Become the middle: ARP-spoof, then read the traffic

The two Act-1 mechanisms fired at once. Remember the ARP slide: it's an unauthenticated broadcast — anyone can lie. Here you do. First press Victim logs in while normal: the traffic goes straight to the gateway, your capture pane is empty (a switch only sends frames to their real destination). Now hit Spoof ARP: you send forged replies telling the victim "I'm the gateway" and the gateway "I'm the victim" — both cache your MAC, and the path visibly bends through you. Log in again: now the victim's packets cross your machine, and the capture pane shows the cleartext HTTP login — password=Summer2026!. Finally flip the victim to HTTPS: you're still in the middle, but you relay only encrypted Application Data — no password. Lands the whole arc: this is why HTTPS-everywhere matters, and why "inside the LAN" is not "safe." Real tools: Ettercap, Bettercap, arpspoof. This also seeds Day 5 — ARP spoofing is noisy and detectable, which the defender will catch.

Act 2 · escalate · first principles

Who's allowed to do what on Linux — and the bit that leaks power

-rwsr-xr-x
owner (root) group others (you) the SUID s
Every file lists read/write/execute for three audiences. Here ls -l shows a root-owned file with an s where owner's x should be — that's the trapdoor.

Users & root

Every process runs as some user (a uid). root (uid 0) can do anything. You landed as low-priv alice.

Goal: become root on this box.

rwx × 3

read, write, execute — listed for owner, group, and others. That's the -rwxr-xr-x string.

Others = you, unless you own it.

The SUID bit

An s in the owner slot: the program runs as its owner, not as you. A root-owned SUID program you can abuse = a root shell.

Power leaks from owner to runner.

sudo & cron

sudo runs a command as root (sometimes with no password); cron runs jobs on a schedule (sometimes as root). Misconfigure either → a way up.

Both are top escalation leads.
Privilege escalation = finding one such misconfiguration — not a movie exploit. On the next slide, three leads work and one is a trap; the trap teaches that writable ≠ exploitable.
The foundation the privesc sandbox completely assumes. Walk the permission string once, out loud: dash, then three triples (owner/group/other), each r-w-x; “others” is you. Then the four leads the toy uses — uid/root, the rwx model, the SUID bit (power runs as the owner, so a root-owned SUID binary is a trapdoor), and sudo/cron misconfigs. Land the through-line: escalation is hygiene failures, not 0-days. Prime the trap — /tmp is writable but nothing privileged runs your file there, so writable isn't exploitable. ~85s; without this the sandbox is hieroglyphics.

Act 2 · escalate · low-priv → root

Privilege escalation: turn a misconfig into root

Stage 2 of the loop. You have alice's shell, not root's — escalation is abusing a misconfiguration to become root. Have them click each lead and read the terminal: SUID (a root-owned binary with the s-bit runs as root — abuse it), sudo NOPASSWD find (allowed to run find as root, and find can spawn a shell — GTFOBins), writable cron (a root job you can edit = scheduled root code execution). Then the teaching trap: /tmp writable — click it and it fails, staying alice. Land that: "writable" is not "exploitable"; it only matters if something privileged runs your file. The prompt flips alice$ → root#, uid 1000 → 0. Two lands: (1) privesc is misconfigurations, not 0-days; (2) the fix is hygiene — least privilege, audit SUID/sudoers. Real hunters automate this with LinPEAS/WinPEAS; every technique here is real (toy targets).

Act 2 · loot · first principles

The server never stored your password — just its fingerprint

Summer2026! — one-way hash → 41aed72cec76…
easy this way ▶  ·  ◀ practically impossible to reverse
Systems keep a hash — Day 1's fingerprint — not your actual password. You can't run it backwards. But you can guess and check.

Why a hash, not the password

If the database leaks, the attacker gets fingerprints, not passwords. Verifying a login means hashing what you typed and comparing — the server never needs the plaintext.

Day 1's lesson, now from the loot side.

Cracking = guess & compare

Hash millions of candidate passwords and look for a match — a dictionary (word lists) or brute force. Weak/common falls in seconds; long & random doesn't.

No salt (NTLM): one guess tests every account at once.

Pass-the-hash no crack needed

On Windows/SMB the hash itself is what proves who you are. Steal the fingerprint and you log in without ever knowing the password — strength stops mattering.

A leaked hash = a working key.
So once you've dumped the hashes, you choose: crack the weak ones offline, or pass the strong one's hash straight into a login. The next slide does both, on real NTLM hashes.
Foundation for the credloot toy. Three ideas: (1) storage is one-way hashes, not plaintext — reinforce Day 1 and explain why (a leak yields fingerprints; login = hash-and-compare); (2) cracking is guess-and-compare, bounded entirely by password strength, and NTLM's missing salt means one hash of a candidate tests all accounts at once; (3) pass-the-hash — for NTLM/SMB the hash is the credential, so a strong password can't save a leaked account. Set up the choice the toy offers: crack the weak three, pass the strong one. ~80s.

Act 2 · loot · credential access

Loot the credentials: crack them, or just reuse the hash

Passwords are stored as one-way hashes (Day 1) — but a weak one still falls to an offline dictionary in seconds, and for NTLM the hash itself logs you in.
Stage 3 of the loop. Bridge the OS jump explicitly: web01 is Linux, but it runs Samba to serve Windows file shares — and Samba keeps its own password database of NT hashes (the Windows format), which as root you dump with pdbedit. That's how a Linux box hands you Windows-style credentials. (On a real Windows host the equivalent is mimikatz against LSASS or the SAM.) These are the same real NTLM hashes as Day 1's fingerprints — the table computes them live. Press Run dictionary attack: it steps the wordlist, and for each candidate it actually hashes the word and compares. bob (sunshine), alice (Summer2026!) and svc_backup (P@ssw0rd!) match — land that even a "complex-looking" seasonal password with a symbol falls to word+rules. Point out the no-salt line: one hash of a candidate is tested against all four accounts at once, because NTLM adds no per-user salt — that's why it's so weak. The 16-char random administrator password never appears in the list, so it does NOT crack. So press Pass-the-hash: for NTLM/SMB the hash itself authenticates — you log in as administrator to the file server without ever knowing the password. Two lands: (1) password strength decides crack time — length/randomness matter (Day 1, from the attacker's side); (2) pass-the-hash means a strong password can't save an account once its hash leaks — that stolen credential is the fuel for lateral movement next.

Act 2 · the target · what "the domain" means

The domain: one login that opens every machine

The problem it solves

500 computers shouldn't mean 500 separate accounts. So the organisation runs one central directory — Active Directory — holding every user, group and machine.

You get: one username and password, and every company machine accepts it.

The Domain Controller

The server that is that directory. Every login in the building is checked by it.

Which means: it stores the password hash of every account in the organisation — including yours.

Domain Admin

A group whose members are administrator on every domain-joined machine at once.

Not "an admin somewhere" — the admin, everywhere, by design.

Why you aim here

From the DC you can reset any password, read any file share, and push software to every endpoint in the company.

Convenience for IT is the same thing as leverage for you.
This is why the loop ends at the Domain Controller. Every hop you make is really a hunt for one credential the whole domain trusts — and once you hold it, you stop hacking and simply log in.
A definition slide, deliberately not a toy — and it must come before lateral movement, because until now "domain admin" has been an undefined goal. Same discipline as Act 1: teach the mechanism before you weaponise it. Explain it from the IT side first so it doesn't sound sinister: managing hundreds of machines with local accounts is impossible, so Windows networks centralise identity in Active Directory. Then turn each convenience into leverage — (1) one credential works everywhere, so one stolen credential works everywhere; (2) the DC must know every hash in order to check every login, which makes it the single richest target in the building; (3) Domain Admin is a group, not a person, and membership means administrator on every joined machine simultaneously. Land the framing line: attackers don't break into the domain, they authenticate to it — the pass-the-hash from the last slide is the key, and the next slide is the lock. Mention that Linux/macOS shops have equivalents (LDAP, Kerberos realms, SSO/Entra ID) and the logic is identical: centralised identity is a huge security win and a huge single point of failure. Defences arrive Thursday — tiered admin, separate admin accounts, and never letting a domain admin log into an ordinary workstation.

Act 2 · move · lateral movement

Spread: one box at a time, all the way to the domain

Stage 4 — the payoff of the loop. You own web01 (Day 2's foothold) and carry only the loot from the last two slides: alice's cracked password and the local Administrator NT hash. Click the glowing machines to move. Land the key distinction up front: that local-admin hash opens fileserver (the same local account, reused — a real and common technique) but the DC refuses it — a local admin is not a domain credential. So the DC stays locked until you go get one. The only path that yields it is a chain: dev-pc via alice's password (RDP), which drops svc_sql DB creds → db01 via those creds (MSSQL), where a Domain Admin has a live session you steal → only now does the DC light up.
